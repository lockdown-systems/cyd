# X capture findings — 2026-09-14

Observations from the capture work for #709, recorded as they were made.
Each names what was seen, where it bites, and what is still unknown.

## 0. The operation Cyd matches on no longer exists

`UserTweetsAndReplies` was not issued once in a full read walk. X has split it
in two, and renamed both halves:

| Surface          | Route                      | Operation               | Identifier               |
| ---------------- | -------------------------- | ----------------------- | ------------------------ |
| Profile timeline | `/<username>`              | `UserOriginalsTimeline` | `z_JDHIa1yBS42jLdUH1j3A` |
| Replies          | `/<username>/with_replies` | `UserRepliesTimeline`   | `fTdkOgyI3EJPk0Qjlv8qUw` |
| Likes            | `/<username>/likes`        | `Likes`                 | `o000A_Cp4JPOihhbeEgi0g` |
| Bookmarks        | `/i/bookmarks`             | `Bookmarks`             | `tF6KOjmZM0WGcB2Q0mfwhw` |
| Following        | `/<username>/following`    | `Following`             | `4EQGMEhtdVw8NeVBDQHESQ` |
| One post         | `/<username>/status/<id>`  | `TweetDetail`           | `FyR-GrebyjdkRoW1z6uCgQ` |
| One post         | —                          | `TweetResultByRestId`   | `snmujSvB_9WXyd8yjvZ24Q` |

Cyd matches timeline responses on `/UserTweetsAndReplies?`, `/Likes?`, and
`/Bookmarks?`. Likes and bookmarks still match. Posts match nothing at all,
on either route.

## 1. The profile timeline now uses `UserOriginalsTimeline`, which Cyd ignores

Loading `https://x.com/<username>` and scrolling to the bottom issues four
`UserOriginalsTimeline` requests — one per page — for an account with roughly
74 posts.

Cyd recognises a timeline response by matching its URL against
`/UserTweetsAndReplies?`, `/Likes?`, or `/Bookmarks?`
(`src/account_x/controller/index/indexParseTweetsResponseData.ts:40`).
`UserOriginalsTimeline` matches none of them, so every page of posts is
captured by the proxy and then discarded without being parsed.

**Impact:** this is half of the silent zero-posts failure in #710. The job
completes, nothing is parsed, and nothing reports an error.

## 2. `/with_replies` no longer contains original posts

The route Cyd loads to save and to delete posts is
`https://x.com/<username>/with_replies`
(`jobs_index.ts:49`, `jobs_delete.ts:57`). On 2026-09-14 that route returned
**replies only** — four items for an account whose profile timeline held about
74 posts.

**Impact:** the other half of the silent failure. Even with the parsing in
finding 1 fixed, saving from this route would find no original posts, because
X no longer puts them there.

**Consequence for the repair:** posts have to be read from the profile route,
or from both routes, rather than from `/with_replies` alone. Whichever is
chosen, the delete job loads the same route and carries the same referrer, so
both sides move together.

## 2b. Replies arrive inside modules, not as top-level entries

Found while promoting the fixtures, by parsing them rather than by reading
them. `UserRepliesTimeline` returns **no top-level `tweet-` entries at all**.
Each reply is a `TimelineTimelineModule` with the entry id
`profile-conversation-<id>`, whose `items[]` hold the posts:

    profile-conversation-2099637429928460288          TimelineTimelineModule
      profile-conversation-...-tweet-2099594030929842403   TimelineTweet
      profile-conversation-...-tweet-2099594032628576747   TimelineTweet

The two items are the post being replied to and the reply itself. The module's
items carry their content under `item.itemContent`, where a top-level entry
carries it under `content.itemContent` — so the path differs as well as the
depth.

`UserOriginalsTimeline` and `UserRepostsTimeline` are not like this: their
posts are top-level `tweet-<id>` entries.

**Impact:** a parser that walks top-level entries and matches `tweet-` finds
zero replies, even once it is pointed at the right operation. Whatever #710
does about finding 2, it has to descend into modules on the replies route, and
read `item.itemContent` there rather than `content.itemContent`.

## 3. X caps daily posting, and refuses inside an open composer

Seeding stopped at 55 or so posts in a day with "You've hit the daily post
limit. Subscribe to Premium for higher limits." The refusal leaves the composer
open with the text still in it — there is no failed navigation and no error
response to notice.

**Impact:** not a Cyd bug, but it shapes what a test account can hold, and it
is a reminder that X reports refusal inside a successful-looking interaction.

## 4. Reposting is disabled when the author has blocked the viewer

A blocked viewer sees the repost control greyed out, with a slashed-repost
badge in the post header, on every post by the account that blocked them.
Nothing in the response says "blocked".

**Impact:** worth recognising, since X also carries `limitedActionResults`
with `limited_actions[]` naming `Retweet` and `QuoteTweet`. A delete or
unretweet aimed at such a post is a mutation X will refuse, and the delete work
should read that as a refusal rather than as its own failure.

## 4b. The user object has no `legacy` sub-object at all

In a `UserOriginalsTimeline` response, `user_results.result` has no `legacy`
key whatsoever. The author fields live in `core`:

    core: { created_at, name, screen_name }

alongside `avatar`, `banner`, `privacy`, `verification`, `tweet_counts`, and
`relationship_counts`. #707 described this as fields moving out of `legacy`
into `core`; what was actually observed is that `legacy` is gone.

**Impact:** any guard that requires `legacy.screen_name` on the author rejects
every entry, which is the parsing half of the silent failure.

## 4c. The end of a timeline is a page with only cursors

Each timeline ends with a response carrying two `cursor` entries and no `tweet`
entries at all:

| Timeline                | Entries per page              |
| ----------------------- | ----------------------------- |
| `UserOriginalsTimeline` | 20, 20, 13, then cursors only |
| `Likes`                 | 20, 20, 16, then cursors only |
| `Bookmarks`             | 20, 20, 18, then cursors only |
| `Following`             | 19 users, then cursors only   |

**Impact:** that cursor-only response is the "no more" signal, and it is
distinct from an error. Three or more pages are confirmed on posts, likes, and
bookmarks, so the seeded account satisfies what #709 asks for.

## 4d. Likes redirect into the `/i/` namespace

Requests made while on the likes timeline carry referrers of
`https://x.com/i/history/likes` and `https://x.com/i/history`, not
`https://x.com/<username>/likes`. X redirects the old route.

**Impact:** this is the URL-changed error for likes. It also fixes the referrer
that the `UnfavoriteTweet` mutation has to send, which currently points at the
route that redirects.

## 4e. The empty profile timeline is not an empty response

Also found by parsing the promoted fixtures. The empty account's
`UserOriginalsTimeline` returns a who-to-follow module and two cursors — four
entries by the decoder's count, one module and three suggested users — so
"the response has no entries" is not a usable emptiness test either. What is
absent is post entries specifically.

`UserRepliesTimeline` and `UserRepostsTimeline` return two cursors and nothing
else; `Likes` and `Bookmarks` return no entries at all. So the three timelines
disagree about what an empty response looks like, and only "no post entries"
holds across all five.

**Impact:** sharpens finding 7. The test is not "zero entries", it is "a
recognised timeline response carrying zero post entries".

## 5. A repost does not survive its original being deleted

The orphaned retweet was seeded as the ticket asks: a post from a second test
account, reposted, and the original then deleted. Afterwards the repost was not
on the reposting account's profile timeline at all — no tombstone, no
placeholder, nothing to open a permalink for.

**Impact:** the shape #710 has to handle cannot be produced by reading a
timeline. A retweet whose original was deleted can only arise in data Cyd
already saved — saved while the original still existed, and orphaned since — or
on the delete side, when Cyd tries to undo a repost whose original is gone.

That changes what a fixture for it should be. A timeline response containing a
tombstone entry may not be a thing X ever returns; the response worth capturing
is the one X gives when a delete is aimed at a post that is no longer there.

**Confirmed from the capture:** the type census over 521 captured calls lists
`Tweet`, `TimelineTweet`, `TimelineTimelineItem`, `TimelineTimelineCursor`,
`User`, and `TimelineUser`. Neither `TweetTombstone` nor `TweetUnavailable`
appears anywhere. The entry is genuinely gone, and no fixture for it can be
taken from a read.

## 6. The elements the automation clicks are still there

Every selector Cyd depends on was counted on every surface it is used on
(`capture/<date>/selector-census-01-read-main.md`). The DOM is not the problem:

- `section article` and `section [data-testid="cellInnerDiv"]` match on all
  three timelines.
- `div[data-testid="cellInnerDiv"] button button` — the positional unfollow
  selector — matches 19 on the following list, one per followed account.
- **`[data-testid$="-unfollow"]` also matches 19.** The stable identifier #711
  wants exists, so the positional selector can be replaced rather than kept.
- `article[tabindex="-1"]` matches on a post permalink.
- `div[data-testid="emptyState"]` matches nothing on a populated timeline, as
  expected; the empty account will say whether it appears when one is empty.

**Impact:** #710 and #711 are route, operation, and response-shape problems.
The markup is not what broke.

## 7. There is no explicit empty-state signal, and the profile timeline has none at all

Captured from an account with nothing in it.

**In the responses.** Nothing matching an empty-state marker appears anywhere:
no `noResults`, no `emptyState`, no alert entry. What an empty timeline returns
is simply a page with no post entries:

| Timeline                | Entries returned                                   |
| ----------------------- | -------------------------------------------------- |
| `UserOriginalsTimeline` | a who-to-follow module and 2 cursors, **no posts** |
| `UserRepliesTimeline`   | 2 cursors, nothing else                            |
| `Following`             | 2 cursors, nothing else                            |
| `Likes`, `Bookmarks`    | no entries at all                                  |

**In the page.** `div[data-testid="emptyState"]` is present on the empty likes,
bookmarks, and following pages — and **absent on the empty profile timeline**.

| Surface          | `emptyState` present when empty |
| ---------------- | ------------------------------- |
| Profile timeline | **no**                          |
| Likes            | yes                             |
| Bookmarks        | yes                             |
| Following list   | yes                             |

**Impact:** this is the asymmetry #710 describes, confirmed. Likes and bookmarks
can ask the page whether they are empty. The profile timeline cannot: the
marker Cyd would look for does not exist on that page, so no selector would
have helped.

**What distinguishes empty from broken.** Not a marker, but whether a timeline
response was recognised at all:

- A recognised timeline response carrying zero post entries — the account is
  genuinely empty, and the run should finish quietly and successfully.
- No recognised timeline response at all — something is wrong, and the run
  should say so. This is today's failure: no response matched, so nothing was
  parsed, and the job reported success.

That distinction needs no signal from X, and it satisfies both user stories:
the empty account finishes quietly, and the broken run reports an error.

## 8. Every delete referrer Cyd sends is wrong, and one identifier has rotated

Captured by driving X's own interface and recording what its client sent.

| Operation         | Identifier X sent           | Identifier in Cyd           | Referrer X sent                 | Referrer Cyd sends                         |
| ----------------- | --------------------------- | --------------------------- | ------------------------------- | ------------------------------------------ |
| `DeleteTweet`     | `nxpZCY2K-I6QoFHAHeojFQ`    | `VaenaVgh5q5ih7kvyVjgtg` ❌ | `https://x.com/<username>`      | `https://x.com/<username>/with_replies` ❌ |
| `UnfavoriteTweet` | `ZYKSe-w7KEslx3JhSIk5LA` ✅ | same                        | `https://x.com/i/history/likes` | `https://x.com/<username>/likes` ❌        |
| `DeleteBookmark`  | `Wlmlj2-xzyS1GN3a6cj-mQ` ✅ | same                        | `https://x.com/i/history`       | `https://x.com/i/bookmarks` ❌             |

So two of the three identifiers are current and one has rotated — and **all
three referrers are wrong**, not two as #711 assumed. `DeleteBookmark` sends
`/i/history`, not the bookmarks route at all.

Three operations are not GraphQL:

| Action       | Endpoint                                   |
| ------------ | ------------------------------------------ |
| Unfollow     | `POST /i/api/1.1/friendships/destroy.json` |
| Change bio   | `POST /1.1/account/update_profile.json`    |
| Lock account | `POST /1.1/account/settings.json`          |

Cyd drives the last two by typing into settings pages and clicking save. They
are single REST calls.

## 9. Deleting an already-deleted post returns 200 with an empty body

The request X's own client had sent was replayed for a post already deleted.
X answered **HTTP 200 with an empty body** — no error array, no message.

Worth one caveat: the replay did not send the `x-client-transaction-id` header
that X's client generates per request, so the empty body may be a rejection of
the replay rather than X's answer for a missing post. What is certain is that
it is not an error response, and a delete job checking only for HTTP 200 would
read it as success.

## 10. Reposts are not on the profile timeline

`UserOriginalsTimeline` is named for what it returns. No repost entry appeared
in any captured response: no `retweeted_status_result`, no `sourceUserId`. The
only `"retweeted": true` in the capture is the viewer's own relationship to a
quoted post.

The `unretweet` control was never present on the profile timeline either —
counted as absent during the read walk, and an undo-repost step scrolling 25
screens of timeline found nothing to click.

**Impact:** Cyd's retweet deletion loads `https://x.com/<username>`
(`jobs_delete.ts:157`) expecting to find reposts there. They are not there.
They are at `/<username>/reposts` — see finding 11.

## 11. Reposts live at `/reposts`, and undoing one is its own operation

Reposts moved to `https://x.com/<username>/reposts`, which is why
`UserOriginalsTimeline` has none.

| What             | Operation             | Identifier               |
| ---------------- | --------------------- | ------------------------ |
| Reposts timeline | `UserRepostsTimeline` | `_ApdvtK9b54C7Q1LDtMxSA` |
| Undo a repost    | `DeleteRetweet`       | `ZyZigVsNiFO6v1dEks1eWg` |

`DeleteRetweet` is sent with the referrer `https://x.com/<username>/reposts`,
and its variables are **not** what Cyd sends:

    { "variables": { "source_tweet_id": "<the original post's id>" },
      "queryId": "ZyZigVsNiFO6v1dEks1eWg" }

    response: { "data": { "unretweet": { "source_tweet_results":
                 { "result": { "rest_id": "<the original post's id>" } } } } }

Cyd undoes a repost by sending `DeleteTweet` with `tweet_id` set to the
repost's own identifier (`jobs_delete/helpers_tweets.ts:66`). X sends a
different operation, with a different variable, naming the **original** post.

**Impact:** #711 needs a third route, a fourth operation, and the original
post's identifier — which the saved data must therefore carry.

## 12. A rate limit is an HTTP 429 with a plain-text body

Provoked by reloading a timeline hard, 45 times. 158 responses came back 429:

- **Status:** `429`, not a successful status
- **Body:** `Rate limit exceeded` — plain text, not JSON
- **Headers:** `x-rate-limit-limit: 50`, `x-rate-limit-remaining: 0`,
  `x-rate-limit-reset: <epoch seconds>`

The limits bit peripheral calls first — `account_settings`,
`CreatorStudioTabBarItemQuery`, the fleets endpoints — rather than the timeline
operations, which kept answering.

**The disguised form was never seen.** Across every capture — 521, 568, 1453,
and 47 calls — not one response arrived with a successful status carrying an
`errors` array. #707's user story 15 assumes that shape exists; this capture
cannot confirm it. Either it arises under conditions this walk did not reach,
or it no longer happens. Anything built for it should be written defensively
rather than against a fixture nobody has.

## 13. The `Viewer` operation still works, and still returns `legacy`

X's own client never calls `Viewer` any more — it was not issued once in any
walk — so it was asked directly, exactly as Cyd asks it.

It answers **200**, and its user object still has `legacy`, with every field
Cyd reads present: `screen_name`, `description`, `friends_count`,
`statuses_count`, `favourites_count`, `profile_image_url_https`. There is no
`core` sub-object on it at all.

**Impact:** the `legacy` removal in finding 4b applies to the **timeline**
operations' user objects, not to `Viewer`. Cyd's account lookup is not broken
and must not be "fixed" — the two shapes genuinely differ, and the same parsing
cannot serve both.

## 14. Changing the banner is one REST call, behind a crop step

Cyd's banner tombstone job is an unimplemented stub (`jobs_tombstone.ts:19`).
What it needs:

    POST /1.1/account/update_profile_banner.json     referrer https://x.com/

In the page, the flow is: set the file on `input[data-testid="fileInput"]`,
wait for the crop step's `[data-testid="applyButton"]`, then
`button[data-testid="Profile_Save_Button"]`.

Both clicks have to go through the element's own `click()` rather than the
pointer, because the settings dialog keeps a mask in its `#layers` subtree that
swallows pointer events — the same obstacle the composer has. Cyd's
`scriptClickElement` already works this way.

## 15. An empty reposts timeline behaves like the others

`UserRepostsTimeline` on an empty account returns 2 cursors and nothing else,
and `div[data-testid="emptyState"]` is present on the page — so reposts
resemble likes and bookmarks, not the profile timeline, which has no page
marker at all.

## Still unknown

- What X returns when a delete or unretweet is aimed at a post that no longer
  exists, which is where the orphaned-retweet case actually arises.
- Whether X still reports a rate limit inside a successful response, as #707
  assumes. None was seen across four captures.
