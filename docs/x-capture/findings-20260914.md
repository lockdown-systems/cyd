# X capture findings — 2026-09-14

Observations from the capture work for #709, recorded as they were made.
Each names what was seen, where it bites, and what is still unknown.

## 0. The operation Cyd matches on no longer exists

`UserTweetsAndReplies` was not issued once in a full read walk. X has split it
in two, and renamed both halves:

| Surface          | Route                      | Operation               | Identifier               |
| ---------------- | -------------------------- | ----------------------- | ------------------------ |
| Profile timeline | `/<username>`              | `UserOriginalsTimeline` | `z_JDHIa1yBS42jLdUH1j3A` |
| Replies          | `/<username>/with_replies` | `UserRepliesTimeline`   | `fTdkOgyI3EJPk0Qjlv8qUw` |
| Likes            | `/<username>/likes`        | `Likes`                 | `o000A_Cp4JPOihhbeEgi0g` |
| Bookmarks        | `/i/bookmarks`             | `Bookmarks`             | `tF6KOjmZM0WGcB2Q0mfwhw` |
| Following        | `/<username>/following`    | `Following`             | `4EQGMEhtdVw8NeVBDQHESQ` |
| One post         | `/<username>/status/<id>`  | `TweetDetail`           | `FyR-GrebyjdkRoW1z6uCgQ` |
| One post         | —                          | `TweetResultByRestId`   | `snmujSvB_9WXyd8yjvZ24Q` |

Cyd matches timeline responses on `/UserTweetsAndReplies?`, `/Likes?`, and
`/Bookmarks?`. Likes and bookmarks still match. Posts match nothing at all,
on either route.

## 1. The profile timeline now uses `UserOriginalsTimeline`, which Cyd ignores

Loading `https://x.com/<username>` and scrolling to the bottom issues four
`UserOriginalsTimeline` requests — one per page — for an account with roughly
74 posts.

Cyd recognises a timeline response by matching its URL against
`/UserTweetsAndReplies?`, `/Likes?`, or `/Bookmarks?`
(`src/account_x/controller/index/indexParseTweetsResponseData.ts:40`).
`UserOriginalsTimeline` matches none of them, so every page of posts is
captured by the proxy and then discarded without being parsed.

**Impact:** this is half of the silent zero-posts failure in #710. The job
completes, nothing is parsed, and nothing reports an error.

## 2. `/with_replies` no longer contains original posts

The route Cyd loads to save and to delete posts is
`https://x.com/<username>/with_replies`
(`jobs_index.ts:49`, `jobs_delete.ts:57`). On 2026-09-14 that route returned
**replies only** — four items for an account whose profile timeline held about
74 posts.

**Impact:** the other half of the silent failure. Even with the parsing in
finding 1 fixed, saving from this route would find no original posts, because
X no longer puts them there.

**Consequence for the repair:** posts have to be read from the profile route,
or from both routes, rather than from `/with_replies` alone. Whichever is
chosen, the delete job loads the same route and carries the same referrer, so
both sides move together.

## 3. X caps daily posting, and refuses inside an open composer

Seeding stopped at 55 or so posts in a day with "You've hit the daily post
limit. Subscribe to Premium for higher limits." The refusal leaves the composer
open with the text still in it — there is no failed navigation and no error
response to notice.

**Impact:** not a Cyd bug, but it shapes what a test account can hold, and it
is a reminder that X reports refusal inside a successful-looking interaction.

## 4. Reposting is disabled when the author has blocked the viewer

A blocked viewer sees the repost control greyed out, with a slashed-repost
badge in the post header, on every post by the account that blocked them.
Nothing in the response says "blocked".

**Impact:** worth recognising, since X also carries `limitedActionResults`
with `limited_actions[]` naming `Retweet` and `QuoteTweet`. A delete or
unretweet aimed at such a post is a mutation X will refuse, and the delete work
should read that as a refusal rather than as its own failure.

## 4b. The user object has no `legacy` sub-object at all

In a `UserOriginalsTimeline` response, `user_results.result` has no `legacy`
key whatsoever. The author fields live in `core`:

    core: { created_at, name, screen_name }

alongside `avatar`, `banner`, `privacy`, `verification`, `tweet_counts`, and
`relationship_counts`. #707 described this as fields moving out of `legacy`
into `core`; what was actually observed is that `legacy` is gone.

**Impact:** any guard that requires `legacy.screen_name` on the author rejects
every entry, which is the parsing half of the silent failure.

## 4c. The end of a timeline is a page with only cursors

Each timeline ends with a response carrying two `cursor` entries and no `tweet`
entries at all:

| Timeline                | Entries per page              |
| ----------------------- | ----------------------------- |
| `UserOriginalsTimeline` | 20, 20, 13, then cursors only |
| `Likes`                 | 20, 20, 16, then cursors only |
| `Bookmarks`             | 20, 20, 18, then cursors only |
| `Following`             | 19 users, then cursors only   |

**Impact:** that cursor-only response is the "no more" signal, and it is
distinct from an error. Three or more pages are confirmed on posts, likes, and
bookmarks, so the seeded account satisfies what #709 asks for.

## 4d. Likes redirect into the `/i/` namespace

Requests made while on the likes timeline carry referrers of
`https://x.com/i/history/likes` and `https://x.com/i/history`, not
`https://x.com/<username>/likes`. X redirects the old route.

**Impact:** this is the URL-changed error for likes. It also fixes the referrer
that the `UnfavoriteTweet` mutation has to send, which currently points at the
route that redirects.

## 5. A repost does not survive its original being deleted

The orphaned retweet was seeded as the ticket asks: a post from a second test
account, reposted, and the original then deleted. Afterwards the repost was not
on the reposting account's profile timeline at all — no tombstone, no
placeholder, nothing to open a permalink for.

**Impact:** the shape #710 has to handle cannot be produced by reading a
timeline. A retweet whose original was deleted can only arise in data Cyd
already saved — saved while the original still existed, and orphaned since — or
on the delete side, when Cyd tries to undo a repost whose original is gone.

That changes what a fixture for it should be. A timeline response containing a
tombstone entry may not be a thing X ever returns; the response worth capturing
is the one X gives when a delete is aimed at a post that is no longer there.

**Confirmed from the capture:** the type census over 521 captured calls lists
`Tweet`, `TimelineTweet`, `TimelineTimelineItem`, `TimelineTimelineCursor`,
`User`, and `TimelineUser`. Neither `TweetTombstone` nor `TweetUnavailable`
appears anywhere. The entry is genuinely gone, and no fixture for it can be
taken from a read.

## 6. The elements the automation clicks are still there

Every selector Cyd depends on was counted on every surface it is used on
(`capture/<date>/selector-census-01-read-main.md`). The DOM is not the problem:

- `section article` and `section [data-testid="cellInnerDiv"]` match on all
  three timelines.
- `div[data-testid="cellInnerDiv"] button button` — the positional unfollow
  selector — matches 19 on the following list, one per followed account.
- **`[data-testid$="-unfollow"]` also matches 19.** The stable identifier #711
  wants exists, so the positional selector can be replaced rather than kept.
- `article[tabindex="-1"]` matches on a post permalink.
- `div[data-testid="emptyState"]` matches nothing on a populated timeline, as
  expected; the empty account will say whether it appears when one is empty.

**Impact:** #710 and #711 are route, operation, and response-shape problems.
The markup is not what broke.
