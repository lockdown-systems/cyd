# X capture findings — 2026-09-14

Observations from the capture work for #709, recorded as they were made.
Each names what was seen, where it bites, and what is still unknown.

## 1. The profile timeline now uses `UserOriginalsTimeline`, which Cyd ignores

Loading `https://x.com/<username>` and scrolling to the bottom issues four
`UserOriginalsTimeline` requests — one per page — for an account with roughly
74 posts.

Cyd recognises a timeline response by matching its URL against
`/UserTweetsAndReplies?`, `/Likes?`, or `/Bookmarks?`
(`src/account_x/controller/index/indexParseTweetsResponseData.ts:40`).
`UserOriginalsTimeline` matches none of them, so every page of posts is
captured by the proxy and then discarded without being parsed.

**Impact:** this is half of the silent zero-posts failure in #710. The job
completes, nothing is parsed, and nothing reports an error.

## 2. `/with_replies` no longer contains original posts

The route Cyd loads to save and to delete posts is
`https://x.com/<username>/with_replies`
(`jobs_index.ts:49`, `jobs_delete.ts:57`). On 2026-09-14 that route returned
**replies only** — four items for an account whose profile timeline held about
74 posts.

**Impact:** the other half of the silent failure. Even with the parsing in
finding 1 fixed, saving from this route would find no original posts, because
X no longer puts them there.

**Consequence for the repair:** posts have to be read from the profile route,
or from both routes, rather than from `/with_replies` alone. Whichever is
chosen, the delete job loads the same route and carries the same referrer, so
both sides move together.

## 3. X caps daily posting, and refuses inside an open composer

Seeding stopped at 55 or so posts in a day with "You've hit the daily post
limit. Subscribe to Premium for higher limits." The refusal leaves the composer
open with the text still in it — there is no failed navigation and no error
response to notice.

**Impact:** not a Cyd bug, but it shapes what a test account can hold, and it
is a reminder that X reports refusal inside a successful-looking interaction.

## 4. Reposting is disabled when the author has blocked the viewer

A blocked viewer sees the repost control greyed out, with a slashed-repost
badge in the post header, on every post by the account that blocked them.
Nothing in the response says "blocked".

**Impact:** worth recognising, since X also carries `limitedActionResults`
with `limited_actions[]` naming `Retweet` and `QuoteTweet`. A delete or
unretweet aimed at such a post is a mutation X will refuse, and the delete work
should read that as a refusal rather than as its own failure.

## 5. A repost does not survive its original being deleted

The orphaned retweet was seeded as the ticket asks: a post from a second test
account, reposted, and the original then deleted. Afterwards the repost was not
on the reposting account's profile timeline at all — no tombstone, no
placeholder, nothing to open a permalink for.

**Impact:** the shape #710 has to handle cannot be produced by reading a
timeline. A retweet whose original was deleted can only arise in data Cyd
already saved — saved while the original still existed, and orphaned since — or
on the delete side, when Cyd tries to undo a repost whose original is gone.

That changes what a fixture for it should be. A timeline response containing a
tombstone entry may not be a thing X ever returns; the response worth capturing
is the one X gives when a delete is aimed at a post that is no longer there.

**To confirm from the capture rather than by eye:** the decoded summary lists
every GraphQL type seen. If `TweetTombstone` or `TweetUnavailable` appears in a
profile timeline response, X does return something and it simply is not
rendered. If neither appears, the entry is genuinely gone.

## Still unknown

- Which operation `/with_replies` issues now, and whether it is still
  `UserTweetsAndReplies`.
- Whether `UserOriginalsTimeline` carries the same response shape as the old
  operation, or whether the author fields moved as well.
- What the profile timeline returns for an account with no posts at all: the
  explicit empty-state signal that #710 needs to tell "empty" from "broken".
- What X returns when a delete or unretweet is aimed at a post that no longer
  exists, which is where the orphaned-retweet case actually arises.
